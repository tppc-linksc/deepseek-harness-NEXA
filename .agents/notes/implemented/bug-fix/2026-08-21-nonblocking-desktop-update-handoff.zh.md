# Agent Note: 桌面更新发现与安装包交接保持非阻塞

Status: implemented

[English](2026-08-21-nonblocking-desktop-update-handoff.md) | 中文

## 问题

自动发现更新时会在应用上方打开原生模态弹窗，并把一次确认同时视为下载、校验和打开安装包的许可。在 macOS 上，DMG 打开后现有应用仍处于运行状态；用户从 DMG 拖入新版本时，Finder 会因为应用仍在使用而无法完成替换。用户尚未决定下载时，模态弹窗也已经打断当前工作。

## 决策

桌面更新客户端会在全局 `shell.overlay` 插槽中注册可叠加条目，并与“应用更新”设置页共享同一个更新控制器。自动检查会在 renderer 加载前启动，而且只发布主进程状态。浮层加载该状态，并在检查、下载或交接安装包期间轮询。可下载、下载中、已下载、安装中和错误状态会呈现为左下角可交互卡片；安静状态不呈现任何内容。关闭卡片只会在当前 renderer 生命周期内隐藏同一阶段和版本，设置页仍会提供权威操作。

下载与交接安装包是两个独立的明确操作。可下载卡片会启动流式、已校验的后台下载，同时保持应用可用。校验通过后会出现下载完成卡片，并提供当前平台对应的安装操作。暂存元数据仍会持久保存，因此应用重新启动后能够恢复已校验安装包的下载完成状态。renderer 会收到安装包格式，以呈现准确的操作文案，但不会收到暂存路径。

在 macOS 上，`shell.openPath()` 成功交接后会立即调用 `app.quit()`。Finder 可以在应用退出前挂载 DMG，但用户手动拖入替换文件前，旧应用已经关闭。如果 Launch Services 拒绝打开 DMG，应用会保持运行，从而保留错误提醒和可用的设置入口。Windows 对 NSIS 保持同样的“成功打开后退出”规则。Linux 打开 AppImage 后会保持应用运行，因为在单实例持有者退出期间启动新镜像并不是可靠的重启机制。

renderer 私有协议会把 `download` 与 `install` 公开为两个独立的异步路由。组合式 `apply` 路由会直接删除，不保留兼容别名，因为预发行产品没有外部使用方，而且一步操作本身就是缺陷行为。

## 考虑过的替代方案

**保留原生发现弹窗，只在打开 DMG 后退出 macOS 应用。** 这样可以修复 Finder 替换失败，但仍会打断当前工作，也无法把下载许可与发现更新分开。

**后台下载完成后立即打开安装包。** 下载完成可能远晚于用户点击，并可能在没有当前安装决定的情况下终止正在进行的会话。第二次操作可以让这次中断保持明确。

**先退出，再请求 Launch Services 打开 DMG。** Electron 进程退出后无法继续完成进程内 `shell.openPath()` 调用。为了这一顺序增加独立辅助进程会引入新的可执行生命周期，却没有用户收益；先打开不会执行应用代码的 DMG 并立即退出，仍能在用户手动替换前关闭应用。

**使用 Electron `autoUpdater` 完成原地重启。** 本 fork 仍然分发未签名或 ad-hoc 签名的安装包，并有意保留操作系统的手动安装警告。在签名与更新源能够如实支持无人值守替换前，已校验的原生安装包流程仍是合适机制。

## 结果

发现更新不再阻塞工作区。用户可以在下载期间继续工作，在下载完成后推迟安装，并在应用重新启动后恢复已校验的完成状态。macOS 不会再同时呈现已挂载 DMG 与 Finder 无法替换的运行中旧应用。完成操作会准确描述为退出并打开安装包，而不是静默重启或自行替换。

客户端现在只会在活跃阶段以固定短间隔轮询私有状态路由。控制器会排列并发状态响应，并独立释放操作锁，因此轮询不会让检查或下载永久停留在忙碌状态。单元覆盖会固定校验、失败、先打开后退出的顺序、路由分离、响应排序、提醒关闭和阶段恢复。无密钥组装浏览器场景会通过产品 Loader 加载真实构建插件，只模拟 Electron 持有的私有路由，并记录可下载与已下载两种提醒界面。
