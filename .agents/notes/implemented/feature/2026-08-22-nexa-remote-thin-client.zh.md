# Agent Note: 将 NEXA Remote 收敛为无感薄客户端

Status: implemented

[English](2026-08-22-nexa-remote-thin-client.md) | 中文

## 问题

第一版 NEXA Remote 把实现细节暴露成了产品步骤。用户必须进入设置、查看 Relay 状态和标识、扫码、核对指纹、在电脑再次确认、确认配对成功，然后再进入会话；小程序重新编译或重载还可能丢失这段过渡状态。这让安全的远程延伸看起来像另一套系统，也掩盖了最核心的事实：所有任务都由电脑持有并执行，而不是手机。

## 决策

继续让 `qrcode-remote` 作为 Host 持有的 Cordis 运行组件和唯一密码学身份所有者，但把用户入口从设置移到 `sidebar.footer.trailing` 中一个 36 像素的“**连接移动端**”图标，与“设置”处于同一页脚行并紧邻其右侧。点击后只打开一个紧凑浮层，包含自动生成的微信小程序码和一个允许连接开关。Relay 地址、电脑 ID、指纹、重连、待确认 proposal 与已配对设备管理只保留在开发诊断或类型化 Host 控制面，不进入常规产品 UI。

把打开浮层并签发 challenge 视为电脑用户对一个匹配配对 proposal 的显式短时同意。现有签名两阶段协议继续保留：手机对 proposal 签名，电脑对 confirmation 签名。只有 proposal 与当前浮层授权且尚未过期的 challenge 精确匹配时，Host 才能自动提交电脑确认；成功、过期、被新 challenge 替换或 Host 关闭时都必须清空这一单次授权。仅持有 Relay 票据永远不足以授权对端。

微信小程序必须是严格薄客户端。微信扫码启动小程序后，引导层交换 `scene`、在后台完成握手、恢复加密对端，并立即打开最近的桌面会话。主流程不再提供小程序内扫码、指纹页、配对成功页或进入会话按钮。移动端信息架构镜像电脑每个未归档的工作区和会话，包括刚创建的空白会话，并以响应式导航和固定输入栏呈现对话事件、问题和审批。它可以请求操作，但不能创建本地会话、运行 Agent、调用模型、访问项目文件或执行工具；电脑不可用时，执行能力也不可用。

连接恢复属于基础设施，不是用户流程。Host 只有在传输完成身份认证后才报告已连接；Relay 意外断开后按有上限的指数退避自动重试；浮层请求新配对窗口时会重启已经失效的连接。小程序使用绑定到具体 SocketTask 的回调，并在挂起恢复或网络变化后重新连接。桌面端成功刷新状态后会清除之前的短时连接错误。

投影沿用桌面的信息层级，而不是直接暴露原始执行遥测。小程序展示普通消息和带具体命令、文件或测试目标的紧凑工具动作；参数、过程日志和结果在用户需要前保持折叠，Markdown 通过安全子集渲染。电脑 `running` 快照决定发送或停止，手机取消会路由到电脑 Session。历史页使用低于 Relay 帧上限的编码字节预算，因为即使按条数限制，只要一个工具返回大型终端结果仍可能超过传输上限。已认证业务帧会覆盖延迟的离线 Presence。

## 考虑过的替代方案

**保留完整设置控制台，只改进样式。** 样式无法修复要求用户理解 Relay 与身份实现细节的流程；这些控制对诊断有价值，但不是普通用户任务。

**删除电脑确认签名。** 这会让持有 Relay 票据本身成为充分条件，削弱配对边界。自动提交与 challenge 绑定的电脑签名，既保留协议保证，也移除了重复的可见点击。

**为了响应速度在小程序中加入本地任务运行时。** 这会产生第二个事实来源，重复 Agent 循环与安全策略，并让重连后的状态合并变得含糊。性能应通过紧凑投影、增量事件、输入的乐观展示和清晰离线状态解决。

## 结果与取舍

- 运行组件清单仍能看到 `qrcode-remote`，普通用户入口是“设置”旁的一个紧凑图标，而不是设置分区或全宽导航行。
- 打开入口会自动得到微信扫码直达的小程序码；浮层只显示二维码、人能理解的连接状态和允许连接开关。
- 微信扫码后在后台完成与 challenge 绑定的签名配对，并且无需其他用户操作就打开最近的桌面会话。
- 不同、过期、已替换或已经消费的 challenge proposal 永远不会被自动确认。
- 小程序只渲染电脑提供的工作区、全部未归档会话、历史、实时事件、问题和审批；所有变更都是发给桌面 Host 的请求，最终状态都从电脑返回。
- 桌面端与小程序端会从短时断线中自动恢复，不向用户暴露 Relay 控件。
- 大型桌面历史不会撑爆单个 Relay 帧；移动工具详情默认折叠，Markdown 安全渲染，发送/停止镜像桌面运行状态。
- 设置、包文档、子系统文档、产品文档、测试与快照对薄客户端边界的描述一致。

流程简化后，电脑显式打开二维码的动作和 challenge 精确匹配成为关键安全边界，因此测试固定了授权不能漂移到其他 challenge。直接导航会暴露旧中间页掩盖的加载与重连竞态，因此引导与对端恢复必须有确定性覆盖。紧凑浮层有意放弃内联诊断空间；错误只提供简短用户文案，技术细节进入开发日志，而不重新回到产品 UI。

## 测试

桌面客户端现已注册一个 `sidebar.footer.trailing` 图标，用紧凑小程序码浮层替代设置分区。`qrcode-remote` 签发与当前 challenge 精确绑定、单次有效的授权；Host 继续保留签名两阶段协议，并拒绝不匹配或过期 proposal。Host 与小程序会在短时断线后恢复完成身份认证的传输，小程序同时投影空白与活跃的未归档桌面会话。

侧边栏、远程控制客户端与 Host 适配层定向测试覆盖页脚几何、旧错误清理、认证连接状态和空白会话同步。固定版本的 NEXA Remote 依赖也分别通过密码学、信封、Relay、Host、小程序与端到端测试，并覆盖超大历史字节分页、紧凑工具卡、安全 Markdown、移动抽屉以及由桌面权威驱动的运行/停止状态。完整 GUI、文档、Web 构建与桌面打包门禁继续作为更广泛薄客户端的发布基线。
