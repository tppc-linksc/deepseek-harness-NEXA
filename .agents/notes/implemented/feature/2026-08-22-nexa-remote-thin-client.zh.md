# Agent Note: 将 NEXA Remote 收敛为无感薄客户端

Status: implemented

[English](2026-08-22-nexa-remote-thin-client.md) | 中文

## 问题

第一版 NEXA Remote 把实现细节暴露成了产品步骤。用户必须进入设置、查看 Relay 状态和标识、扫码、核对指纹、在电脑再次确认、确认配对成功，然后再进入会话；小程序重新编译或重载还可能丢失这段过渡状态。这让安全的远程延伸看起来像另一套系统，也掩盖了最核心的事实：所有任务都由电脑持有并执行，而不是手机。

## 决策

继续让 `qrcode-remote` 作为 Host 持有的 Cordis 运行组件和唯一密码学身份所有者，但把用户入口从设置移到名为“**连接移动端**”的 `sidebar.footer.action`。点击后只打开一个紧凑浮层，包含自动生成的微信小程序码和一个允许连接开关。Relay 地址、电脑 ID、指纹、重连、待确认 proposal 与已配对设备管理只保留在开发诊断或类型化 Host 控制面，不进入常规产品 UI。

把打开浮层并签发 challenge 视为电脑用户对一个匹配配对 proposal 的显式短时同意。现有签名两阶段协议继续保留：手机对 proposal 签名，电脑对 confirmation 签名。只有 proposal 与当前浮层授权且尚未过期的 challenge 精确匹配时，Host 才能自动提交电脑确认；成功、过期、被新 challenge 替换或 Host 关闭时都必须清空这一单次授权。仅持有 Relay 票据永远不足以授权对端。

微信小程序必须是严格薄客户端。微信扫码启动小程序后，引导层交换 `scene`、在后台完成握手、恢复加密对端，并立即打开最近的桌面会话。主流程不再提供小程序内扫码、指纹页、配对成功页或进入会话按钮。移动端信息架构镜像电脑的工作区、会话、对话事件、问题和审批，只做响应式导航和固定输入栏。它可以请求操作，但不能创建本地会话、运行 Agent、调用模型、访问项目文件或执行工具；电脑不可用时，执行能力也不可用。

## 考虑过的替代方案

**保留完整设置控制台，只改进样式。** 样式无法修复要求用户理解 Relay 与身份实现细节的流程；这些控制对诊断有价值，但不是普通用户任务。

**删除电脑确认签名。** 这会让持有 Relay 票据本身成为充分条件，削弱配对边界。自动提交与 challenge 绑定的电脑签名，既保留协议保证，也移除了重复的可见点击。

**为了响应速度在小程序中加入本地任务运行时。** 这会产生第二个事实来源，重复 Agent 循环与安全策略，并让重连后的状态合并变得含糊。性能应通过紧凑投影、增量事件、输入的乐观展示和清晰离线状态解决。

## 结果与取舍

- 运行组件清单仍能看到 `qrcode-remote`，普通用户入口是一个侧边栏底部操作，而不是设置分区。
- 打开入口会自动得到微信扫码直达的小程序码；浮层只显示二维码、人能理解的连接状态和允许连接开关。
- 微信扫码后在后台完成与 challenge 绑定的签名配对，并且无需其他用户操作就打开最近的桌面会话。
- 不同、过期、已替换或已经消费的 challenge proposal 永远不会被自动确认。
- 小程序只渲染电脑提供的工作区、会话、历史、实时事件、问题和审批；所有变更都是发给桌面 Host 的请求，最终状态都从电脑返回。
- 设置、包文档、子系统文档、产品文档、测试与快照对薄客户端边界的描述一致。

流程简化后，电脑显式打开二维码的动作和 challenge 精确匹配成为关键安全边界，因此测试固定了授权不能漂移到其他 challenge。直接导航会暴露旧中间页掩盖的加载与重连竞态，因此引导与对端恢复必须有确定性覆盖。紧凑浮层有意放弃内联诊断空间；错误只提供简短用户文案，技术细节进入开发日志，而不重新回到产品 UI。

## 测试

桌面客户端现已注册一个 `sidebar.footer.action`，用紧凑小程序码浮层替代设置分区。`qrcode-remote` 签发与当前 challenge 精确绑定、单次有效的授权；Host 继续保留签名两阶段协议，并拒绝不匹配或过期 proposal。小程序引导层会在后台恢复或建立加密对端，然后直接重启到适配手机的桌面会话投影。

客户端与运行组件定向测试通过（2 个文件、13 项），定向 TypeScript 与 Oxlint 通过，完整 GUI 回归通过（289 个文件、3,995 项通过、1 项跳过），完整 Web 构建也通过。Web replay 启动快照仍会在远程 UI 挂载前失败，因为 NEXA Local Build 不包含该上游快照硬编码要求的官方 DeepSeek 标识；本次没有通过修改无关断言来掩盖这个既有品牌基线差异。
