# Agent Note: 桌面发行更新在安装前完成校验

Status: implemented

[English](2026-08-18-verified-desktop-updates.md) | 中文

## 问题

桌面 fork 独立于 DeepSeek Harness 官方发行版发布原生安装包。用户需要在 App 内从发现版本进入正确的安装包，且不能把官方上游发行误认为 NEXA 桌面发行、下载错误操作系统或 CPU 架构的安装包，或信任未完成的下载。维护者也需要在官方仓库发布新版 Harness 时收到可靠信号，但不能直接转发上游发行，因为桌面载体可能需要源码集成与回归处理。

## 决策

桌面 bundle 包含只在桌面组合中启用的更新插件，由它调用 Electron 主进程私有路由。独立的“应用更新”设置页会显示已安装的 NEXA 版本，支持手动检查，保存每日自动检查的用户选择，并展示下载进度。面板采用三行受限布局：当前版本、自动检查的语义化 switch，以及手动检查操作和紧邻的状态信息；下载进度与后续安装操作按需显示在其下方。提醒与安装包交接时机由后续的[非阻塞桌面更新交接](../bug-fix/2026-08-21-nonblocking-desktop-update-handoff.md)决定，它取代了最初的一步确认：发现版本时保持非阻塞，下载由一次明确操作启动，打开已校验安装包则是下载完成后的独立操作。Web UI 与其他 bundle 不加载该插件，更新流程不会增加 HTTP 监听，也不会把更新状态暴露到 Electron 进程之外。

`tppc-linksc/deepseek-harness-NEXA` 的 GitHub Releases 是桌面更新的权威来源。客户端通过 Releases API 发现稳定版和预发行版，忽略草稿，识别 `nexa-v<semver>` 与旧版 `desktop-v<semver>` 两类 tag，并选择最高语义版本。不高于当前安装版本的发行即使没有清单也表示已是最新；更高版本必须包含 `stable.json` 资产，而且清单版本必须与所选 tag 一致。更高版本缺少发布资料、请求限流、传输失败、其他 HTTP 失败和无效发布资料会分别呈现不同结果。

每个已发布版本严格包含当前三个受支持目标各一个安装包：macOS ARM64 DMG、Windows x64 NSIS EXE 和 Linux x64 AppImage。每项原生构建都会在打包前拒绝不完整的部署运行时：macOS 要求 PTY addon 与可执行的 spawn helper，Windows 要求两个 ConPTY addon 及其兼容库和 OpenConsole 辅助程序，Linux 要求 PTY addon。原生构建任务全部结束后，发行工作流根据这些安装包生成 `stable.json` 与 `SHA256SUMS.txt`。语义版本包含预发行后缀的标签会创建 GitHub prerelease；稳定版本会成为最新稳定版。清单记录 NEXA 版本、发行说明、已集成的上游版本和提交，以及每个安装包的平台、架构、安装器类型、文件名、URL、字节长度和 SHA-256 摘要。客户端只接受受支持的清单版本、属于 fork 仓库的 HTTPS 链接、预期的安装包扩展名和大小上限内的文件。

下载以 `.part` 后缀流式写入更新专用私有目录。管理器在传输期间限制声明的字节长度和最大体积，只有在计算并核对 SHA-256 后才提升文件并保存暂存元数据。启动恢复会重新计算摘要，再决定是否恢复暂存安装包；打开安装包前还会再次计算，因此下载后被修改的文件会被拒绝。macOS 打开 DMG 后退出正在运行的 App，Windows 打开 NSIS 安装器后退出正在运行的 App，Linux 为 AppImage 增加执行权限后将其打开。系统无法打开安装包时，App 会保持运行。应用不会静默替换自身，不会执行清单提供的源码，也不会把摘要校验描述成代码签名。

定时上游监控会比较 DeepSeek 官方 `deepseek-ai/deepseek-harness` 发行 tag 与 `.nexa/upstream.json`。发现更新的官方 tag 后，它会创建唯一的仓库 issue，列出新旧上游版本和提交。维护者审核并集成变更，更新 `.nexa/upstream.json`，运行桌面检查，再通过受保护的 `desktop-release` 环境发布独立版本号的 NEXA 发行版。发现官方上游更新永远不会自动发布安装包。

## 考虑过的替代方案

**使用 Electron `autoUpdater` 无人值守替换应用。** 它的生产路径依赖签名与平台特定更新源，而本 fork 当前发布未签名或 ad-hoc 签名的安装包。打开已校验的原生安装包可以为三个受支持目标提供一致行为，也不会把手动安装包装成静默更新。

**每次更新都把用户送到 Releases 页面。** 这样可以删除下载代码，但用户必须自行识别目标并手动校验摘要。私有更新插件能够确定性地完成这些选择，并且不需要修改桌面组合之外的官方 Harness 界面。

**把 DeepSeek 官方发行作为客户端更新源。** 官方 tag 不提供本 fork 的 Electron 安装包，也不能说明哪个 NEXA 源码版本已经完成集成。因此只有 NEXA 发行可以成为客户端可见的更新权威来源。

**上游监控发现 tag 后自动发布。** 即使只是依赖更新，也可能改变内嵌 Web UI、session 格式、插件加载或桌面打包。由维护者完成集成和发行审批，可以在分发前审核这些变化。

## 结果

桌面用户会收到每日自动提示，也可以从独立设置页手动检查；版本、偏好与检查状态不会再让设置弹窗横向溢出。一次操作只下载当前平台安装包、展示进度并校验体积与摘要，后续操作会再次校验并打开安装器。更新文件和偏好不会与 Web UI session 或设置共用。检查、下载或打开安装包失败都不会影响已安装应用继续运行，未完成文件也不会被提供安装。

桌面发行仓库及其 HTTPS 分发仍然属于信任基础：与安装包同时发布的 SHA-256 能识别意外损坏和下载后的修改，但无法抵御发行权威本身被攻破。操作系统的未签名警告和手动安装仍然存在。维护者必须集成官方更新、更新已记录的上游版本、批准发行环境，并保持清单与三个原生安装包一致。
